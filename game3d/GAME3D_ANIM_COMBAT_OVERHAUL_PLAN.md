## WHY THIS DOC EXISTS
Hiro vibe-checked the current `game3d/arena.html` build and it looks janky, not "Dragon's Crown pro." Specific complaints, verbatim intent preserved:
1. Walking/idle animation is janky and funny-looking, not smooth. Wants it to look like the friend's "Tencent animator" result — a 2D sprite that moves smooth and clean, comparable to how characters read in Dragon's Crown (you see every step, decent idle, crisp/detailed attacks).
2. Summons (dragon, succubus, claw demon, etc.) stack on top of the warlock and block the view of him. They should keep distance from the warlock, and IF overlap is unavoidable in 2D, they must render BEHIND him, never in front. Each summon type should move with its own distinct AI/behavior (dragon flies, succubus hovers, claw demon runs), not orbit him.
3. Attack VFX (fireball, acid breath) still look like tiny top-down-game sprites/particles ("little tiny fireballs on the ground going in lines," "little tiny green circle breath spray") — they were never re-scaled or re-styled for the new side-on painterly presentation. Needs a full visual overhaul to match the DC art direction.
4. No walk-to-next-encounter beat. Right now clearing a wave instantly pops the next wave into the same spot. Dragon's Crown walks you across the pit to the next cluster of enemies between fights.

## ROOT CAUSE (confirmed against the live code, not guesswork)
- `arena.html` line ~1435: `this.anims.create({key:akey, frames, frameRate:(/_idle$/.test(setName)?5:9), yoyo:true, repeat:-1})` — every action is only **3 keyframes**, played forward-then-backward (yoyo) at 5-9fps. Three ping-ponging poses will never read as a clean stride no matter how good the art is.
- `game3d/tools/gen_sprites.py` line 71: `KEYPOSE = {1:"anticipation / wind-up", 2:"contact / peak of the action", 3:"recovery / follow-through", ...}` — every keyframe set, including WALK and IDLE, is generated using attack-pose language. A walk cycle doesn't have a "wind-up/peak/follow-through" — it needs contact → passing → contact poses. This is why walking reads as fidgeting/attacking instead of striding.
- On top of those 3 keyframes, `arena.html`'s `foeMotion()` (~line 1752, tagged "FEEDBACK #8: stride bob + lean + squash/stretch + step dust") ALSO applies procedural bob/lean/squash-stretch to the same sprite every frame. Two motion systems stacked on one 3-frame flipbook is what reads as glitchy/wobbly rather than smooth.
- Summon render code (`summonDemons()` ~1096, `updDemons()` ~1136, the `demonSprites` Map ~1520/2604) has a "lane" render offset for side-on display but no enforced minimum distance from the warlock and no depth rule that puts summons behind him when a lane conflict happens — hence the "sticking to him" complaint.
- Fireball/acid-breath VFX (`fireballs.push(...)` at ~870/1172/1190, `fireBurst()` ~2237, `fxBreath()` ~2252, gas-cloud draw ~2492) still use the small `fireball.png`/particle-scale sizing carried over from the original top-down `game/` — never went through the same `SPRITE_TARGET_H` scale-normalization pass the characters got.
- Wave advance (`arena.html` ~1319-1320: `if((S.fight|0) < GAUNTLET_N-1){ S.fight++; spawnFight(S.fight); ... }`) fires the instant the last enemy dies — there is no travel/transition state, hence the "pop up" feel.

**The workaround, LOCKED:** build the rig-like consistency entirely in code instead of a rig tool — a **programmatic cutout hierarchy**. Grok generates each body part ONCE (static, transparent bg, on-model from the existing approved references) instead of a whole pose per frame; Fable builds a simple parent/child part tree in Phaser (containers, which Phaser supports natively) and animates it by hand-authoring rotation/position keyframes per action, interpolated via Phaser tweens. Same core insight as rigging (one piece of art, transformed by math = zero drift) with zero GUI-tool dependency — 100% written in code by Fable. No mesh deformation (parts rotate rigidly, they don't stretch/bend), so it won't be quite as organic as true Vanillaware skin-deform, but it eliminates the drift problem entirely and reads as continuous motion, not a flipbook — which is the actual complaint.
**Explicitly rejected alternative:** single-shot multi-frame sprite-sheet generation (one Grok call per action instead of N). Rejected by Hiro as "too rigid, will ultimately limit animations" — still a fixed discrete-frame ceiling, just a more consistent one. Do not pursue this instead of the cutout hierarchy.

## PHASE 2 — FIX THE KEYFRAME SOURCE (free pipeline, more frames + correct poses)
**Change, in `gen_sprites.py`:**
1. Split the `KEYPOSE` vocabulary by action type instead of one-size-fits-all: attacks keep anticipation/contact/follow-through; **walk** gets a real stride vocabulary (e.g. contact-pose-left, passing/mid-stride, contact-pose-right, passing/mid-stride — a true loopable cycle, not yoyo); **idle** gets 1-2 subtle poses (weight-shift/breathing), not a wind-up pose.

## PHASE 2B — PROGRAMMATIC CUTOUT RIG, WARLOCK PILOT (supersedes Phase 2 as the character-body motion source)
**Why this exists:** Phase 2 helped but has a ceiling — every new pose is a fresh Grok call, so drift and cost both scale with however many frames/actions you ever want. This phase trades "generate more frames forever" for "generate each body part ONCE, animate it forever for free in code." This is the direct fix for the repeat-generation waste problem — parts are reusable across every action and every future tweak; only entirely NEW parts ever need a new Grok call.

**2B.1 — Part inventory + ONE-TIME generation.** Look at the existing approved Warlock references (`warlock_idle.png`, `warlock_walk_*.png`, etc. — reference only, do not try to reuse them as parts, they're full-body composites) and define a fixed, named part list — something like: `head`, `torso_robe_upper`, `arm_staff_upper`, `arm_staff_fore`, `hand_staff` (or staff as its own part), `arm_off_upper`, `arm_off_fore`, `robe_lower` (a single skirt/cloth piece, not separate legs — robes hide individual leg motion, so don't over-segment). Generate each part exactly ONCE via Grok, on-model (edit from the existing reference), transparent background. This is the only Grok spend in this phase — a fixed, small, named list, not an open-ended batch.
**Acceptance:** every named part exists as its own transparent PNG in `art_in/`/ingested to `assets/sprites/`, visually on-model with the existing approved Warlock look.
**Generation-time discipline (get this right now, expensive to fix later):** every part is a SEPARATE Grok call, so the prompt must pin down a consistent light direction / rim-light source across ALL of them (e.g. "lit from upper-left, cool teal rim-light on the right edge, matching the approved warlock_idle reference") — otherwise rotating parts will look like each one carries its own independent light source, which reads as fake no matter how good the rig/timing is. Check this by eye across all generated parts before moving to 2B.2; regenerating one mismatched part now is cheap, discovering it after the rig is built is not.

**2B.2 — Pivot manifest.** For each part, determine its pivot/anchor point (the joint it rotates around — e.g. the forearm pivots at the elbow, not its image center) and record it in a small JSON manifest (`{"part":"arm_staff_fore","pivotX":..,"pivotY":..}`). This can be eyeballed from the generated part images — doesn't need to be perfect, just physically plausible.
**Acceptance:** manifest exists with a pivot entry for every part in 2B.1.

**2B.3 — Hierarchy + timing templates in code.** Build the parent/child part tree in `arena.html` (Phaser containers: torso is root, arms/head attach to torso, forearm attaches to upper arm, etc.) using the pivots from 2B.2. Author reusable timing templates (JSON, same spirit as the research doc's own good idea) per action — `idle` (subtle sway/breathing), `walk` (a real stride cycle: leg/robe swing, arm counter-swing, torso bob), `attack` (windup → active → recovery) — as keyframed rotation/position values per part over time, referencing the existing Phase 2 art (this week's 94 images) as visual reference for how each pose should look.
**Acceptance:** `node --check` passes; a dry-run/log confirms the hierarchy builds without errors and the timing template data validates (right part names, no missing pivots).
**Quality techniques (do these, they're cheap and are what separates "smooth" from "stiff/puppety" in rigid cutout animation):** (a) slight overlap between connected parts at each joint (e.g. the upper-arm layer extends slightly past the elbow, forearm draws on top) so rotation never reveals a gap or seam; (b) give the `robe_lower` piece its OWN independent sway curve, offset/lagging slightly behind the torso's motion (secondary motion / follow-through) rather than rotating rigidly in lockstep — this single trick reads as "alive cloth" instead of "rigid pendulum" for very little extra work; (c) use eased interpolation (ease-in/ease-out, not linear) between keyframes so motion has weight and doesn't feel mechanical; (d) on the attack's impact frame, hold/freeze briefly (an "impact freeze," a few frames of no motion) before the recovery eases out — this reads as weight/force and is a well-known cheap trick, not extra art.

**2B.4 — Playback, Warlock only.** Wire per-frame interpolation between the timing template's keyframes (Phaser tweens or a manual eased lerp) driving the part hierarchy, replacing the flipbook (`anims.create`/`loadAnimFrames`) system FOR THE WARLOCK ONLY — leave summons/enemies on the existing Phase-2 flipbook system for now. Gate this behind a flag if useful so it's easy to compare old vs. new side by side.
**Acceptance:** Warlock's idle/walk/attack all play as continuous part-transform motion in `arena.html`, no discrete pose-snapping.

**2B.5 — Vibe check (Hiro, in-game, not a screenshot from Fable's sandbox).** Open the real game, watch the Warlock idle, walk, and attack. This is the actual test of the whole pivot: does part-based motion read as meaningfully smoother/more alive than the flipbook did, closer to the Dragon's Crown feel? **Do not templatize to summons/enemies until this is a clear yes.** If it's not convincing, stop and report back rather than guessing at fixes — this is worth a real conversation, not more autonomous iteration.

**Order vs. the rest of the plan:** do 2B before Phase 4 (VFX) — this is the single biggest open question in the whole project (does the cutout approach actually deliver the smoothness Hiro wants) and everything else is secondary until it's answered. Phase 3 (already shipped) and Phase 4/5 remain valid regardless of how 2B turns out.

## PHASE 2C — MOTION POLISH (Hiro pre-approved 2026-07-04; do NOT start until 2B.5's vibe-check is a clear yes)
These are the next tier up from 2B.3's baseline quality techniques — still code-only, no new Grok spend, but hold off on all of them until the basic rig is proven, so effort isn't spent polishing something that might still need structural rework.
1. **Motion arcs, not straight lerps.** Real movement sweeps along a curve (a swinging arm doesn't move point-to-point) — interpolate position along a slight arc/bezier between keyframes instead of a straight line, especially for the attack swing and the walk cycle's limb swing.
2. **Bigger anticipation + follow-through overshoot.** Before a heavy attack, coil back further and hold a beat longer than feels natural at first (anticipation reads as force); after the attack's impact-freeze, let the recovery slightly overshoot the final rest pose before settling back, rather than stopping dead at the end position. Both are standard animation-principle tricks, pure timing-curve numbers, no new art.
3. **More independently-lagging secondary motion.** Beyond the robe (already in 2B.3): the staff crystal's glow pulsing on its own cycle, a cloak edge or hair strands lagging slightly behind the body's motion. Same trick as the robe sway, applied to more small elements — each one cheap, adds up to "alive."
**Acceptance:** re-run the same in-game vibe check as 2B.5 — does adding these make the Warlock's motion read as meaningfully more weighted/alive, not just busier? If a technique doesn't visibly help, don't keep it just because it's on this list.
**Honest ceiling note:** even with all of 2B + 2C done well, this is "genuinely good cutout animation," not literally indistinguishable from Vanillaware's full mesh-deform rigging (which requires manual GUI rigging Hiro has explicitly ruled out). That's an acceptable outcome, not a failure — revisit only if Hiro decides the gap still matters after seeing this in motion.
**Deferred, not forgotten:** once the Warlock pilot (2B + 2C) is approved, the same part-hierarchy treatment needs to extend to summons and enemies for a consistent cast-wide look. Do not start this until the Warlock pilot is a clear yes.

## PHASE 3 — SUMMON DISTANCE, DEPTH, AND INDEPENDENT AI
**Change:**

2. Depth rule: if a summon's lane position would visually overlap the warlock (2D space is a strip, unlike the enemies), the summon renders at a LOWER depth than the warlock's sprite (behind), never above/in front. Never let a summon occlude his read.
3. Per-type movement behavior (this is new, not currently modeled — confirm against `updDemons()` ~1136 per-type branches):

   - **Claw fiend / brute:** ground-based — runs toward its target when aggroing, runs/backs off when retreating; normal ground-plane movement, no float.
   - All of the above already have their own AI/attack logic in `updDemons()` — this phase is specifically about (a) enforcing the distance/depth rule and (b) giving each type its own idle/traversal MOTION so they don't all default to the same "restless lean" bob currently shared by the crowd/foe code.
**Acceptance:** During a fight with 2+ summons active, the warlock's silhouette stays clearly readable at all times — no summon sprite sits on top of him. Dragon visibly flies above the ground line; succubus visibly hovers; claw fiend visibly runs on the ground. None of them idle in place glued to the warlock's position.
